# muxostandoff

ХВХ-рум для Standoff 2: комнаты только для читер против читера. Чистым игрокам здесь нечего делать.

Сайт — один файл `index.html` (HTML + CSS + JS внутри). Без сборки, без npm, без внешних библиотек и CDN.
Работает и по `file://`, и на GitHub Pages.

```
index.html    весь сайт
README.md     этот файл
.nojekyll     отключает Jekyll на GitHub Pages
```

---

## Быстрый старт

1. Открыть `index.html` двойным кликом. Сайт сразу работает в локальном режиме.
2. Зарегистрироваться: Standoff 2 ID (7–12 цифр) → «Проверить» → ник подтягивается из проверки → пароль.
3. Создать комнату, скопировать код `MX-AB12` и позвать второго игрока.

Локальный режим хранит аккаунты и комнаты в `localStorage` браузера. Комнаты видны только в этом браузере
и только на этом устройстве — другие люди их не увидят.

## Firebase Realtime Database (общие комнаты)

Пока `databaseURL` пустой, сайт работает локально. Чтобы комнаты стали общими, подключите базу.

### 1. Создать проект

1. Открыть [console.firebase.google.com](https://console.firebase.google.com/), «Создать проект».
2. В проекте: **Build → Realtime Database → Create Database**.
3. Выбрать регион (например, `europe-west1`) и режим **Test mode**.
4. Скопировать ссылку вида `https://xxx-default-rtdb.europe-west1.firebasedatabase.app`.

### 2. Вписать ссылку в сайт

В `index.html`, в самом верху `<script>`, есть блок настроек:

```js
const CONFIG = {
  databaseURL: "",      // https://xxx-default-rtdb.europe-west1.firebasedatabase.app
  verifyEndpoint: "",   // проверка ника: вернуть {"nick":"Ник"} или 404
  demoVerifyDelay: 700
};
```

Вставить ссылку без завершающего `/` и без `.json`:

```js
databaseURL: "https://xxx-default-rtdb.europe-west1.firebasedatabase.app",
```

Перезагрузить страницу. Внизу должно появиться «база: облако · список общий для всех».
С этого момента список комнат общий для всех, кто открыл сайт, а изменения приходят в реальном времени.

### 3. Rules

**Test mode** открывает базу на чтение и запись всем, у кого есть ссылка. Это простой вариант для игры
«свои против своих», но данные может испортить любой, кто узнает адрес базы. Правила по умолчанию:

```json
{
  "rules": {
    ".read": true,
    ".write": true
  }
}
```

Более аккуратный вариант — открыть только нужные ветки:

```json
{
  "rules": {
    "users": {
      ".read": true,
      ".write": true
    },
    "rooms": {
      ".read": true,
      ".write": true
    },
    ".read": false,
    ".write": false
  }
}
```

Важно: у сайта нет своего бэкенда и нет Firebase Auth. Клиент пишет в базу напрямую, поэтому любые
ограничения на сервере не смогут отличить владельца комнаты от постороннего. Проверки «только владелец
может править и удалять» и «пароль комнаты» работают в интерфейсе. Если нужна настоящая защита — нужен
свой прокси/бэкенд и Firebase Auth, это уже другая задача.

### Как сайт работает с базой

| Операция | Запрос |
| --- | --- |
| список комнат | `GET {databaseURL}/rooms.json` |
| аккаунт | `GET {databaseURL}/users/{standoffId}.json` |
| регистрация | `PUT {databaseURL}/users/{standoffId}.json` |
| создать комнату | `PUT {databaseURL}/rooms/{roomId}.json` |
| правка комнаты | `PATCH {databaseURL}/rooms/{roomId}.json` |
| удалить комнату | `DELETE {databaseURL}/rooms/{roomId}.json` |
| live-обновления | `new EventSource("{databaseURL}/rooms.json")`, события `put` / `patch` / `cancel` |

Записи отправляются с `Content-Type: text/plain`, чтобы браузер не делал CORS-preflight: Firebase
одинаково разбирает JSON в теле запроса. Чтение и поток идут обычным GET.

Если `databaseURL` пустой или база недоступна (нет сети, неверная ссылка, закрыты правила), сайт сам
переключается на `localStorage`. Внизу страницы это видно по строке состояния:

* `база: облако · список общий для всех` — Firebase подключён;
* `база: локально (только у тебя)` — `databaseURL` пустой;
* `облако недоступно · локальный режим` — база была указана, но не ответила.

## Проверка ника Standoff 2

Публичного API Standoff 2 у сайта нет, поэтому по умолчанию работает **демо-проверка**:
ник считается детерминированно из ID — один и тот же ID всегда даёт один и тот же ник,
задержка около 0.7 секунды, на кнопке «Проверяю…». Аккаунт создать без успешной проверки нельзя,
и ник вручную не вводится.

Чтобы подключить настоящую проверку, укажите `verifyEndpoint` — свой маленький прокси:

```js
verifyEndpoint: "https://your-proxy.example.com/standoff?id={id}",
```

Контракт:

* запрос `GET` (плейсхолдер `{id}` заменяется на ID; если плейсхолдера нет, ID добавляется как `?id=`);
* успех — HTTP 200 и JSON `{"nick": "Ник"}`;
* ID не найден — HTTP 404 (сайт покажет «ID не найден в Standoff 2»);
* остальные ошибки — тост «Проверка ника недоступна».

Прокси нужен потому, что браузер не может ходить в закрытые API Standoff 2 напрямую: понадобится
серверная функция с вашим ключом. Пока его нет — демо-режим, и это честно написано в интерфейсе.

## Как выложить на GitHub Pages

### Вариант 1: через сайт GitHub

1. Создать публичный репозиторий, например `muxostandoff`, без автоинициализации.
2. Загрузить в корень `index.html`, `README.md`, `.nojekyll`.
3. **Settings → Pages → Build and deployment**: Source `Deploy from a branch`, Branch `main`, папка `/ (root)`.
4. Дождаться сборки и открыть `https://{owner}.github.io/muxostandoff/`.

### Вариант 2: через git и API

```bash
git init
git add index.html README.md .nojekyll
git commit -m "muxostandoff"
git branch -M main
git remote add origin https://github.com/{owner}/muxostandoff.git
git push -u origin main

gh api --method POST repos/{owner}/muxostandoff/pages \
  -f "source[branch]=main" -f "source[path]=/"
```

Проверка:

```bash
gh api repos/{owner}/muxostandoff/pages/builds/latest
curl -I https://{owner}.github.io/muxostandoff/
```

`.`nojekyll` обязателен: без него GitHub Pages прогоняет файлы через Jekyll, и это может ломать
отдачу статики. Сайт работает и без сборки — это просто статический `index.html`.

Если позже впишете `databaseURL`, помните: файл `index.html` лежит в публичном репозитории, ссылка на
базу тоже будет видна всем. Секретов в ней нет, но правила доступа к базе надо настроить.

## Что умеет сайт

* **Аккаунты по Standoff 2 ID** — регистрация только после проверки ID, ник берётся из проверки,
  пароль хранится хешем (FNV-1a, не крипто), сессия переживает перезагрузку.
* **Комнаты** — 1x1, 2x2, 3x3, 4x4, 5x5 и «Свой размер» на 2/4/6/8/10/12/14 слотов (до 7x7).
  Название до 42 символов, обязательный стиль чита, карта, регион, необязательные пароль и пинг.
* **Стиль чита** — легит / семи-рейдж / рейдж, бейдж на карточке и в окне комнаты, отдельный фильтр со счётчиками.
* **Комната** — код `MX-AB12` с копированием, команды A и B, занятые и свободные слоты, полоса
  заполненности, «Занять слот» / «Выйти» / «Готово».
* **Права** — править и удалять может только владелец, удаление подтверждается вторым кликом.
  Владелец не может «выйти» из своей комнаты: только удалить. У чужой комнаты кнопок правки нет.
* **Пароль комнаты** — при входе поле, сверка по хешу, ошибка «Неверный пароль».
* **Список** — фильтры «Все», форматы, «Свой», «Мои» и стиль чита; поиск по названию, карте, региону,
  нику владельца, никам игроков и стилю; сортировка: сначала неполные комнаты, потом новые.
* **Пустая база** — это норма: «Пока никто не создал комнату. Будь первым.» Никаких демо-комнат и
  придуманных игроков, список наполняют только реальные люди.
* **Темы** — чёрная и белая, переключатель ☀ / ☾ в шапке, выбор запоминается.
* **Мобильная вёрстка** — карточки в одну колонку, команды A/B друг под другом, фильтры переносятся.

## Схема данных

```js
users/{standoffId} = { id, nick, pass, createdAt }

rooms/{roomId} = {
  name, mode,            // "1x1".."5x5" | "custom"
  cap,                   // всего слотов
  map, region, ping,
  style,                 // "legit" | "semi" | "rage"
  passHash, ownerId, ownerNick, code, createdAt,
  players: { "{playerId}": { id, nick, at } }
}
```

Отличия от минимальной схемы, о которых стоит знать:

* `ping` — необязательное число мс, вводится при создании/правке; `null`, если не указан.
* в объекте игрока есть необязательное поле `ready` (bool) — это состояние кнопки «Готово»;
  без него отметку готовности негде хранить в заданной схеме.
* `roomId` — ключ в базе, внутри объекта комнаты его нет; `id` есть только у пользователя.
* `passHash` у комнаты — `hash(пароль + код комнаты)`, у аккаунта — `hash(пароль + ID)`.
  Хеш простой и детерминированный, это защита «чтобы не лежало открытым», а не криптография.
* `code` — публичный код вида `MX-AB12`, он уникален среди существующих комнат.

В локальном режиме те же объекты лежат в `localStorage` под ключами `mx_users`, `mx_rooms`,
`mx_session`, `mx_theme`.

## Ограничения

* Проверка ника по умолчанию демонстрационная (см. выше).
* Кто угодно с доступом к базе может писать в неё напрямую — интерфейсные проверки прав и пароля
  не заменяют серверную авторизацию.
* Одновременное вступление двух игроков в последний свободный слот может переполнить комнату:
  REST без транзакций. Для игры «свои против своих» это редкий и поправимый случай.
* Восстановления пароля нет: аккаунт привязан к ID, при утере пароля нужен новый ID.
* Локальный режим не синхронизируется между браузерами и устройствами.

## Проверка

Сайт прогнан автотестами на DOM (jsdom) с реальными HTTP и SSE-запросами к мок-базе, повторяющей
REST-семантику Firebase. Проверены: пустой список, полный цикл регистрации и входа, ошибки входа,
создание комнаты с паролем, вступление вторым аккаунтом, неверный пароль, правка, удаление вторым
кликом, фильтры и поиск, заполненная комната, темы, сохранение сессии, живое обновление двух браузеров
через SSE, деградация в локальный режим, `file://`, экранирование HTML.
